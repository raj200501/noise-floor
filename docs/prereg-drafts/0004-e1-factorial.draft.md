## Questions

All three concern this suite and these models; none is a claim about real-world tasks or public
leaderboards.

- RQ1 (variance components). How is the latent-scale variance of success split among task,
  model-by-task, model, harness, wall-clock timeout, step budget, sampling temperature,
  concurrency, day, and time-of-day block? The model adds the fixed logistic residual pi^2/3,
  which absorbs run-to-run sampling and every interaction the model leaves out; it is reported
  as such and is not called sampling. Run-to-run sampling itself is measured on the probability
  scale from replicate runs of two fixed configurations. Of the brief's resource limits, the
  step budget (the agent's budget of model replies or tool calls) is estimated; CPU and memory
  are held fixed (one llama-server with 4 threads on 4 CPUs, 16 GB), so E1 estimates no CPU or
  memory component (D-033 item 5).
- RQ2 (minimum detectable effects). For a paired comparison of two models on designs with the
  task and run counts of common leaderboards (20, 40, 89, 200, and 500 tasks, times 1, 3, and 5
  runs per model and task), at the variance components estimated here and not those of any
  leaderboard, what is the smallest difference in success rate detected with power 0.8 at
  two-sided level 0.05 (normal approximation), and how many tasks resolve gaps of 0.02, 0.05,
  and 0.10?
- RQ3 (model and scaffold). What is each model's harness effect (native harness minus
  minimal-agent), does it differ between local models, and how do the Claude tiers compare with
  each other under each harness and with the local models?

## Hypotheses and decision rules

No direction is presumed for any effect.

- Fixed factors (RQ1). For each of the eight fixed factors (model, harness, timeout, steps,
  temperature, concurrency, day, block): H0, its contribution to the linear predictor's variance
  is 0; H1, it is positive. H0 is rejected when the factor's task-jackknife interval (Analysis
  item 1) has its lower end above 0. The eight readings are not adjusted for multiplicity; G6
  reports how often the reading holds for concurrency, planted at 0.
- Contrasts (RQ3). For each comparison of Analysis items 4 and 5: H0, the difference is 0,
  against a two-sided H1. H0 is rejected (the contrast is "supported") when its Holm-adjusted
  p-value within its family is below 0.05. The six families are local harness contrasts, Claude
  harness contrasts, local harness differences, local model pairs, Claude tier pairs, and
  Claude-local pairs.
- Estimation targets, reported with intervals and no test: the random variances and every share
  (RQ1), the MDE and tasks-needed rows (RQ2), the success rates, the sampling table, and the E3
  bounds.

## Design

The run plan is generated by `noisefloor.e1` from the ```json e1-plan``` block. The
preregistered run ids are those of `local_plan` and `claude_plan` for that block. The ```json
e1-design``` block records the SHA-256 of the canonical JSON of every planned run
(`plan_sha256`), every local model's weights and server settings (`model_pins`: repository,
revision, file, SHA-256, the model's llama-server arguments, and the context per slot), the
llama-server build and the SHA-256 over its binary and the shared libraries beside it
(`llama_server`, `noisefloor.models.server_build_sha256`), and the task manifest SHA-256 and
suite version. The runners refuse to start unless this file is frozen and committed, the code
computes the same plan hash, pins, task manifest, and suite version, and the G6 and E0 part 2
artifacts are banked; the local arm's first batch also needs the pinned llama-server digest, or
one that a ```json llama-server``` block of a frozen amendment of this file names (a rebuilt
server, a deviation; D-034). Each batch then checks its run code (D-033 item 10): it does not
start from uncommitted changes under `src/` or to the lock or project file, and run code other
than the arm's first banked run's (the `src/` tree, the lock, and for the local arm the
llama-server build, its binary and shared libraries) stops the arm until a resume accepts it,
reported as a deviation.

- Local models: the s3 candidates (exploratory, suite version 2) with an s3 success rate from
  0.2 to 0.8 and an s3 median wall time under 150 s, the shorter E1 timeout (D-025; s3 ran while
  other work shared the CPU, D-024): LOCAL_MODELS_SENTENCE. Both Qwen3 models run with thinking
  off through the chat template; every server runs the pinned llama.cpp build with `--jinja` and
  `--seed 0`.
- Local arm: each local model runs each of the LOCAL_TASKS_N tasks 16 times, the runs of a half fraction of
  five two-level factors in which an even number of factors are at their second listed level
  (order of `e1-plan.levels`; with the first level coded -1, I = -ABCDE). Every factor is
  balanced inside every (model, task) cell, 8 runs at each level:
  - harness: minimal-agent (this project's scaffold) or `native`, Inspect's basic agent;
  - timeout: wall-clock limit of 150 or 300 seconds per run;
  - steps: step budget of 8 or 15, counted as model replies for minimal-agent (a reply that does
    not parse still uses a step) and as tool calls for Inspect;
  - temperature: sampling temperature 0.0 or 0.7;
  - concurrency: 1 or 2 runs in flight on one llama-server with that many parallel slots, each
    slot with a context of 32,768 tokens (D-018, D-032).
- Replicates (D-028 item 3): each (model, task) cell also runs two configurations a second time,
  minimal-agent with 300 s and 15 steps at temperature 0.0 and concurrency 1 (the MDE reference
  configuration) and at temperature 0.7 and concurrency 2, with their own sampling seeds. That is
  REPLICATE_RUNS_N replicate runs and LOCAL_RUNS_N local runs in all. Replicates enter only the sampling table.
- Batches and schedule (D-027, D-033): runs are grouped into planned batches of at most 10 runs
  that share one model and one concurrency level (one server configuration). Each (model,
  concurrency) group's batches are dealt round robin, from a random offset, over eight slots:
  four days, each with two UTC time-of-day blocks (00:00 to 12:00 and 12:00 to 24:00). The
  `duration_estimate` of the `e1-design` block gives each slot's hours at the dry run's rates (a
  planning estimate). The arm's first batch starts within 15 minutes after 00:00 UTC (launched
  later, the runner waits for the next 00:00 UTC), and day 1 is that UTC date. A batch of slot
  day k, block b starts only in block b of the arm's day k or a later day, the earliest
  unfinished eligible batch first; a slot that overruns its block continues in the same block of
  the next day. Day and block enter the analysis as those of each executed batch's start: a
  planned batch finished after a stop runs as two pieces, each with its own start. If the arm
  uses another number of UTC dates than four, day enters with as many levels as occur; if so, or
  if any executed batch runs off its planned slot (`schedule` in `variance_components.json`), the
  day and block components and shares are reported as resting on a design that G6 and E0 part 2
  did not simulate.
- Replication over days (D-033 item 4): each (model, task) cell runs its half fraction once,
  dealt over the four days, with day and block as fixed blocking factors; no day holds a full
  replicate of a cell.
- Claude slice (run on Raj's machine, D-019, D-030, D-033): each Claude tier (haiku, sonnet,
  opus) runs the first 6 tasks of each family (30 tasks) twice, once with minimal-agent and once
  with Claude Code (`native`), with the two timeouts split by task so that harness and timeout
  are balanced within every task and tier and every tier runs the same timeout under one harness
  on each task. The plan runs complete (tier, task) pairs back to back, tasks in a fixed random
  order and tiers taking turns, so a slice that ends early leaves complete pairs balanced over
  tiers. The step budget is 8 turns: a run whose turn cap (`claude_agent_max_turns` times the cap
  share) would be below 8 is refused before it starts, and the analysis leaves out any banked run
  whose recorded turn cap differs from its `steps` factor. Temperature is the CLI's default and
  no reply cap reaches the CLI. Tiers run by their CLI alias; every run records the model ID and
  the Claude Code version the CLI reports. The slice starts only after
  `python -m noisefloor.claude_arm smoke` printed SMOKE: PASS on that machine, and its stops are
  checked before every (tier, task) pair (Stopping rules). The suite's difficulty was set on the
  local models and the tiers could not be piloted here, so Claude success above 0.8 is expected;
  that is a deviation from brief section 4, reported beside the Claude results (D-033 item 3).
- Tasks: for each of the five families, seeds 100000 to TASK_SEED_LAST with difficulties 1, 2, 3
  in rotation (LOCAL_TASKS_N tasks; the Claude slice runs seeds 100000 to 100005 of each family;
  task manifest SHA-256 in `e1-design`).
- Machine: the local arm runs on this project's hosted machine (4 CPUs, 16 GB of memory, no
  swap), one llama-server with 4 threads at a time on the pinned GGUF files, every subject run in
  the OS sandbox of D-012. Nothing else CPU-heavy runs while the arm runs a batch: tests,
  simulations, and pushes wait for the gaps between blocks. Every run record carries the host's
  load average, its available memory, the server's resident memory, and its run code. The
  Claude slice runs from one clone on Raj's machine, which alone writes its run, stop, and
  ledger files.
- Commands: `python -m noisefloor.e1 plan prereg/0004-e1-factorial.md` (prints the plan hash),
  `python -m noisefloor.e1 local prereg/0004-e1-factorial.md` (the local arm),
  `python -m noisefloor.e1 claude prereg/0004-e1-factorial.md` (the Claude slice, daily),
  `python -m noisefloor.e1 stop local|claude --reason "..."` (a defect stop),
  `python -m noisefloor.e1 resume local|claude --note "..." [--amendment prereg/NNNN-....md]`
  after a repair, `python -m noisefloor.e1 end claude --reason "..."` (an early end, a
  deviation), `python -m noisefloor.e1 note local|claude --reason "..."` (an event that stops
  nothing, such as runs lost with a container), and
  `python -m noisefloor.analysis.e1 build prereg/0004-e1-factorial.md` then
  `python -m noisefloor.analysis.e1 --verify` for the tables.

## Outcome, run accounting, and exclusions

- Outcome: 1 if the suite's grader accepts the run, 0 otherwise (D-021: answers pass through the
  one extraction rule; the strict grade is kept as `outcome_strict` for a sensitivity analysis).
  A run that ends at a limit (wall clock, step budget, or context) has status `timeout` and keeps
  its graded outcome: 0 for the answer families, which have no answer at a limit, and the grade
  of the final file for derive. The number of timeout runs with outcome 1 is reported per model.
- Confirmatory run: a planned run id, banked with this file's path and chain SHA-256, that
  started at or after this file's freeze time.
- A run is banked once, when it ends, and is never run again whatever its status. A run that is
  interrupted (a crash or a restart) or refused before or while it runs (billing guard, daily
  cap, plan usage limit, paid extra usage, a turn cap below the step budget, the kill switch) is
  not banked and runs again from the beginning under its planned run id and seed. Completed but
  unbanked runs are banked from their work directories. A run id banked twice fails the analysis
  and G7. The hosted machine's container is not persistent: banked runs are committed and pushed
  at check-ins (in the gaps between blocks while the local arm runs), and runs banked after the
  last push and lost with a container are recorded in the stop log (`note`) and run again under
  their planned run ids, a deviation.
- Batch-level failures (D-028 item 7, D-029): a batch fails as a whole when the model file fails
  its hash check, the server does not start, the server fails its health check after a run that
  did not end `ok`, three runs in a row end `infra_error`, or the runner exits before every run is
  recorded. The runs the failure did not touch are banked; the failing runs, every run recorded
  after the batch aborted (whatever its status), and the runs that never started are not banked
  and run later under their planned run ids. An `infra_error` run outside such a failure (an
  isolated backend or harness failure) stays banked. A Claude pair is a two-run batch, so in the
  Claude slice three `infra_error` runs in a row across pairs stop the slice instead, and those
  runs stay banked.
- Exclusion: runs with status `infra_error` are left out of the primary analyses (items 1 to 7
  and 10 below); item 8 keeps them as ambiguous runs and item 9 counts them as failures in one
  sensitivity fit. Claude runs on another model ID than their tier's first run, from a Claude
  Code harness child that did not start clean (plan login, only the allowed tools, no MCP
  servers, no memory files), or at another turn cap are left out of every analysis. The
  clean-start check covers the Claude Code harness; minimal-agent steps are single calls with
  `--tools ""` and `--strict-mcp-config`, and every Claude stream refuses an API-key login. `variance_components.json`
  (`exclusions`), `scores.json`, and `contrasts.json` (`excluded`) report these counts per arm and
  reason. There is no other exclusion.
- G7 counts a task run toward its floors (1,000 runs, 150 on Claude tiers) when it is
  confirmatory and the primary analyses use it; the three-day requirement counts local-arm runs.
  Below 150 such Claude-tier runs G7 is reported as failing.
- Nothing about outcomes is read before an arm ends: the arm logs only banked and infra_error
  counts and infra_error end reasons, `artifacts/e1/local.jsonl` and `claude.jsonl` are read
  only by the runners, and the analysis refuses to run until both arms have ended. The local arm
  ends when every planned run is banked or the clock has passed day 7 of the arm; the Claude
  slice when every planned run is banked or its runner has recorded an end point on the machine
  that runs it (Stopping rules).

## Analysis

The settings are in the ```json e1-analysis``` block, which `python -m noisefloor.analysis.e1`
reads. The analysis, its `--verify`, and the post-E1 check run only under the analysis code that
G6 and E0 part 2 ran: the hash of the files in `noisefloor.provenance.ANALYSIS_CODE` (those that
compute these intervals and their validation, and the modules they take the plan, exclusion
rules, and model families from), the lock, and the Python, NumPy, SciPy, pandas, R, lme4,
Matrix, BLAS, and LAPACK versions (`noisefloor.provenance.analysis_code`), recorded in both
artifacts. Other analysis code, or a recomputation in another environment, is refused unless a
frozen amendment of this file allows it in a ```json analysis-code``` block that names that
code's hash (`{"allows": "<hash>"}`), which is a deviation; the outputs, the post-E1 check's
included, name the analysis code they ran.

1. Variance decomposition (RQ1), local arm: logit GLMM by lme4 `glmer` with the Laplace
   approximation (`nAGQ = 1`), the outcome on fixed factors model, harness, timeout, steps,
   temperature, concurrency, day, and block, with random intercepts for task and for
   model-by-task. Components: the two random-effect variances, the variance over runs of each
   fixed factor's contribution to the linear predictor, and the logistic residual pi^2/3; shares
   of their sum. The fit tries the optimizers bobyqa, Nelder_Mead, and nloptwrap in that order
   and uses the first that fits without an error, which the output names. A fit with
   convergence warnings is reported as fitted, with its warnings and `converged: false`; any
   refit chosen after seeing it (another optimizer, or `nAGQ = 0`) is exploratory. If no
   optimizer fits, `variance_components.json` and `mde.json` say not estimable, every other table
   is banked, and G7 fails. A component, share, or MDE row without an interval also fails G7.
   - Random variances and the MDE rows: parametric bootstrap with B = 200, each replicate drawing
     new random effects and outcomes from the fitted model and fitted afresh with the same
     settings and the optimizer that fitted the original; random variances use the RANDOM_RULE
     rule and MDE rows the MDE_RULE rule. A replicate that fails is dropped and counted; a random
     variance, an MDE row (and the tasks-needed rows mapped from it), or the residual share whose
     replicates more than 10 percent failed gets no interval.
   - Fixed contributions: task jackknife (D-028 item 1, D-029). Each coefficient's interval is
     its estimate plus or minus the t quantile on G - 1 degrees of freedom times its
     delete-one-task jackknife standard error over the G refits that succeed (LOCAL_TASKS_N
     refits, so JACKKNIFE_DF_N degrees of freedom when all succeed), at the Bonferroni level for the factor's
     coefficients, and the contribution's interval is its range over that box. The jackknife
     resamples whole tasks, so it keeps variation of the factor effects across tasks that the
     parametric bootstrap, which simulates from the main-effects model, leaves out. A refit that
     fails is dropped; with more than 10 percent of the refits failed, or fewer than 3 left, the
     factor gets no interval. The block's `box_interval` names the exploratory bootstrap box of
     pilot 6 and has no effect here.
   - Shares: the SHARE_RULE rule: each component's interval mapped through v / (v + rest), with
     the rest of the total at its estimate, so a fixed component's share maps its jackknife box;
     the residual share takes the percentile interval of its replicate shares. This interval
     ignores the sampling error of the rest and is approximate.
   - The rules for random variances, shares, and the MDE were chosen by the D-023 protocol on
     exploratory pilot 6 (`artifacts/method_pilots/summary.json`, pool `nagq1-e1-shape`, key
     `choice`), which simulated four models, 30 tasks, 3 days, task variance 2.0, and the
     earlier global batch-to-slot assignment (D-027), with fixed boxes from the bootstrap and
     MDE rows at three designs. The jackknife and the shares mapped from it were checked on exploratory pilot 7 (3
     models, task variance 4.0, 30 tasks; pools `pilot7a-jackknife` and `pilot7b-jackknife`, key
     `check`; the share check was added after pilot 7 ran, D-033 item 8). Every kind met the
     D-028 headline rule there, so every kind is a headline kind; E0 part 2 (0005) and G6 (0006)
     validate them on fresh seeds at this design.
2. MDE table (RQ2): at the reference configuration (minimal-agent, 300 s, 15 steps, temperature
   0.0, concurrency 1; day and block averaged with weights equal to their shares of the runs),
   the fitted model implies, for every pair of local models, the between-task variance of the
   per-task difference in success probability and the within-task run variance
   (`evalstats.design_from_logit`); their means over pairs give the MDE of a paired comparison
   at two-sided alpha 0.05 and power 0.8 for every design in the block, by the normal
   approximation. Under the paired t test the power at that MDE is somewhat below 0.8 for 20 and
   40 tasks. The tasks needed for each gap (0.02, 0.05, 0.10) and each runs value (1, 3, 5) come
   with an interval: the matching MDE interval's ends mapped through n = ceil(T x MDE^2 / gap^2),
   which is monotone in the same per-task variance, so its coverage is at least that of the MDE
   interval. The rows with 3 and 5 runs assume independent runs and carry the reading of item 6.
3. Success rates: local models with task-clustered t intervals (`cluster_t`, LOCAL_TASKS_N tasks x 16 runs);
   Claude tiers with `cluster_wilson`, a Wilson interval at the design-effect sample size (30
   tasks x 2 runs), which stays inside [0, 1] near the ceiling. E0 part 2 includes `cluster_t`
   cells at 2 runs per task near the ceiling as reported extras beside the Wilson cells.
4. Harness contrasts (RQ3): for each local model, native minus minimal-agent on its LOCAL_TASKS_N tasks
   (`cluster_t`, 8 runs per harness per task); for each Claude tier, Claude Code minus
   minimal-agent (`mover_wilson`, 1 run of each per task, within the tier; each task's pair
   also differs in timeout, the longer timeout alternating between the harnesses by task).
   Harness differences (D-028 item 6): for each pair of local models, the first model's harness
   contrast minus the second's, paired by task (`evalstats.contrast_difference`, `cluster_t`).
5. Model comparisons (RQ3): every pair of local models on minimal-agent runs (`cluster_t`, 8 runs
   per model per task); every pair of Claude tiers under each harness (`mover_wilson`, 1 run per
   side, the same timeout on both sides); and each Claude tier against each local model on
   minimal-agent runs with a step budget of 8 only (`mover_wilson`, 1 Claude run against 4 local
   runs per task, on the 30 Claude tasks). These Claude-local comparisons are not crossed with
   the scaffold and are labeled scaffold-confounded (`label`), with every known difference
   (`confounds`): Claude runs at the CLI's default temperature, with no reply cap (the 384-token
   cap reaches only the local server), each step sent as one role-tagged prompt, and its timeout
   alternating between 150 and 300 s by task (D-033 item 6).
6. Sampling table (RQ1, D-028 item 3, D-031): each replicate pairs with the planned run of the
   same model, task, and configuration, when both are usable. Per configuration, the mean over
   tasks of the per-task mean of (y1 - y2)^2 / 2 estimates the within-configuration outcome
   variance, which equals E[p (1 - p)] when repeated runs are independent; its interval is half
   the task-clustered Wilson interval of the share of discordant pairs. The row of the MDE reference configuration
   also reports the E[p (1 - p)] the MDE assumes there, per model and as their mean. Reading:
   when that mean lies above the upper end of the reference row's interval, repeated runs at the
   reference are not independent draws, and the MDE rows with 3 and 5 runs and their tasks-needed
   rows are labeled as resting on a violated independence assumption. The reading treats the
   implied E[p (1 - p)] as known and ignores its estimation error, so it has no stated
   false-positive rate.
7. Supported: as in Hypotheses and decision rules. The unadjusted 95% interval and p-value are
   reported beside each contrast; a `mover_wilson` p-value inverts its interval. Neutral
   reporting (rule 15): every ordering is reported as supported or not supported by this rule,
   and nothing is said about why.
8. E3 (policy-sensitivity bounds), on the confirmatory local-arm runs other than replicates
   (`artifacts/e1/e3_bounds.json`, source e1): ambiguous runs are those with status
   `infra_error`, `timeout`, or `flagged` (E1 has no flagging step, so no run is flagged). For
   each local model, its score under every policy and the worst-case bounds with Imbens and
   Manski intervals; the ranking of the local models under each policy and the number of
   policies whose ranking differs from `as_scored`; and for each adjacent pair in the `as_scored`
   order, the worst-case bounds on the difference with their Imbens and Manski interval and the
   identified and robust readings. No E0 cell has the shape of the pair intervals, which are
   reported as unvalidated.
9. Sensitivity, reported beside the primary results and not replacing them: the decomposition
   with a random intercept for the planned batch (exploratory, D-022), with `outcome_strict`, and
   with `infra_error` runs counted as failures. No E0 cell backs their intervals, which are
   reported as unvalidated. The batch-term fit's batch variance runs low (D-022), so the rule
   uses a bounded upper end: the upper 97.5 percent quantile of that fit's finite bootstrap
   replicate batch variances (`batch_var_upper` in `sensitivity.json`; the `basic_log` upper
   end grows without bound as its lower quantile nears 0). If that exceeds 0.05, or the
   batch-term fit fails or gives no such value (more than 10 percent of its replicates failed),
   the primary intervals for concurrency, day, and block are reported as not validated.
10. Post-E1 check (D-028 item 4, D-031, D-033): 200 datasets (seeds 980000 to 980199) simulated
   at the E1 estimates and analyzed by the unchanged primary analysis, MDE rows included
   (`python -m noisefloor.post_check run|bank prereg/0004-e1-factorial.md`). The planted values
   come from one auxiliary fit of the primary model with task-by-harness, task-by-steps, and
   task-by-timeout random terms added: its fixed effects, variances, and task-by-factor
   variances, planted together (if that fit fails, the primary fit without interactions,
   labeled). The task truth, also behind the MDE truths, is the planted task variance plus half
   of each task-by-factor variance, which the primary model's task term targets; the planted
   batch variance is item 9's `batch_var_upper` (0 when the batch-term fit failed or gave none);
   and the simulated batches are those of the E1 plan, replicate placeholders dealt in and then
   left out. A component whose coverage fails the G5 rule there is reported as resting on an
   unsupported method. G7 requires its artifact (`artifacts/e1/post_check.json`), run under
   the analysis code of the E1 tables.

Every headline interval above has coverage cells in prereg 0005, mapped in its ```json
headline``` block, and G6 (0006) checks the decomposition, MDE, and local-arm intervals on the
E1 design. A kind of interval is backed by all of its cells: if any of them fails G5, every
interval of that kind is reported as resting on an unsupported method and G5 fails. The only
other route is dated amendments frozen before the first confirmatory E1 run: one of prereg 0003
that adds headline cells of the kind for the new method and lists the replaced cells in its
block ```json retired-headline``` (G5 then requires the new cells to pass, prereg 0005); one of this
file that allows the new analysis code; and, for a GLMM kind, one of prereg 0006 that reruns G6
with the new method on new seeds. The labels that rest on other banked artifacts (underpowered
families from `family_verdicts`, the fixed factors' power from G6's `above_zero`, and a kind
resting on an unsupported method) are applied by the report from those artifacts (D-034). Each interval's point estimate is compared with the span its kind's cells
validate (0005's ```json validated-range``` block: differences in absolute value, the sampling
table by its within-configuration variance, the E3 bounds by each model's ambiguous share); an
estimate outside it is reported as outside the validated range (`outside_validated_range`).

## Sample size and power

Brief section 5 asks for sample sizes from the preregistered power analysis under the section 8
caps. The ```json e1-power``` block, generated by `tools/prereg_blocks.py` from code and banked
artifacts (D-032, D-033, D-034), gives for every row of every confirmatory contrast family, at assumed
effects stated in the block and the planted variances: the power of one comparison at
two-sided alpha 0.05, the power of the Holm reading within the family when every member has
that effect (fixed-seed simulation, the smaller over test correlations 0 and 0.5), both with
the family's test statistic (`test`: t on tasks - 1 degrees of freedom for the `cluster_t`
families, each member with its own chi-square draw for its standard error, and normal for the
Wilson families), and the tasks one comparison needs for power 0.8 (normal approximation; the
Holm reading needs more). The local sample is the smallest number of tasks per family at which
every local harness contrast and local model pair has Holm power of at least 0.8 under its t
test: TASKS_PER_FAMILY_N tasks per family, LOCAL_TASKS_N tasks (D-033 item 1, D-034; the
block's `sizing`). The section 8 caps bind the Claude slice at 6 agent runs a day at cap share
0.2; its size is the G7 floor with a margin, 3 tiers x 30 tasks x 2 runs = 180 runs.

- A family whose smallest Holm power in the block (`family_verdicts`) is below 0.8 is reported
  as underpowered beside its results, and a non-supported contrast there is not read as evidence
  of no difference. The rows are design calculations at assumed effects, indexed by planted model
  positions, not statements about particular E1 models.
- For the fixed factors, the power of the reading in Hypotheses is the G6 share of datasets whose
  jackknife interval's lower end is above 0 at the planted values (`above_zero` in
  `artifacts/g6/recovery.json`, banked before any E1 data): a factor below 0.8 there is reported
  as underpowered. Concurrency is planted at 0, so its share is the reading's false-positive
  rate. The exploratory pilot-7 shares at 30 tasks are in the block as planning information.

## Stopping rules

- The local arm runs the whole plan. It stops for repair, and records why in
  `artifacts/e1/stops-local.jsonl`, when a batch fails as a whole, when a batch banks nothing
  because its model calls were refused, when more than 5 percent (and at least 5) of the runs
  banked since its start or last resume are `infra_error`, when its run code changes, or when a
  harness, suite, or grader defect is found (`python -m noisefloor.e1 stop local --reason
  "..."`). A stop takes effect when the running batch (or Claude pair) ends: runs of that batch
  that start after the stop line still run and are banked, and the resume note or the amendment
  lists them by run id and says how they are handled. A stopped arm starts nothing until a
  resume records the repair; a defect stop resumes only under a frozen amendment of this file
  that says how the affected runs are handled and names the stop in a ```json defect-resume```
  block (its `at`). Every stop is reported as a deviation.
- No local batch starts after day 7 of the arm. If the arm has not finished by then, the analysis
  runs on the banked runs and the shortfall is reported as a deviation.
- The Claude slice checks, before every (tier, task) pair: the end point; a Claude Code version
  other than the accepted ones (the slice's first banked version counts as accepted only if a
  smoke run on it passed; it stops until a resume accepts a new version after a smoke run on it
  printed SMOKE: PASS); a banked Claude Code harness child that did not start clean (it stops for
  repair); three `infra_error` runs in a row, in banking order, since its start or last resume
  (it stops for repair); the `infra_error` share, as for the local arm; and its run code. A
  tier served by another model ID than its first run's starts no further run, its runs on the
  other ID are left out and counted, and the other tiers go on (D-033 item 12). The slice ends
  when every planned run of the tiers still served is banked or 45 days after the freeze,
  whichever comes first, and its runner then records an end point in
  `artifacts/e1/stops-claude.jsonl`, at day 45 whatever stop is open (`python -m noisefloor.e1
  claude` run on or after that day records it); an early end is `python -m noisefloor.e1 end
  claude --reason "..."`, a deviation. The slice's stops, resumes,
  and end are recorded only on the machine that runs it (the commands refuse where the billing
  guard is not clean), and its run, stop, and ledger files (`artifacts/e1/claude.jsonl`,
  `stops-claude.jsonl`, `artifacts/usage/ledger-claude.jsonl`) reach the analysis when Raj
  commits them. Below 150 analyzed Claude runs G7 is reported as failing. Each Claude score and
  contrast row records its tiers' complete pairs (tasks with both runs analyzed) and is labeled
  as not matching its E0 cells (`matches_e0_cells`: false) when a tier has fewer than 30.
- One runner per arm holds a lock; each batch runner holds a lock for its own life, and no batch
  starts while any runner under the work root holds its lock, so a relaunch never runs beside a
  live runner; the sandboxed runner gets SIGKILL when the process that launched it dies, and the
  model server stops when its runner dies; records are appended one write each, and a record cut
  by a kill is removed before the next append.
